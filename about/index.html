About FlyFireFighter

A rescue drone with a fly's reflexes and a firefighter in command.

A software harness and digital-twin research prototype. A drone searches outside and inside a burning home, proposes rescue interventions and executes them only under a commander's authority. This page states what is real, what is simulated and what each component is, without claims beyond the implemented code.

What came from the fly

The drone's rendered camera frames feed a pretrained FlyVis connectome-constrained model of the fly visual system (Lappalainen et al., Nature 634, 1132–1140, 2024). It models visual circuitry; it is not an uploaded whole fly brain. Its motion responses go to a readout that proposes braking and turning. Every proposal passes through the harness before any motion executes.

What the cloud deciders do, and what is sent

Mission planner in run setup picks who chooses: the local planner alone; OpenAI Decisions (model gpt-6-luna); Gemini (model gemini-3.6-flash); or consensus, which asks both models in parallel with the same request and uses their choice only when both chose the same candidate. A configured model chooses one of the mission candidates the application has already generated, such as which viewpoint to visit next. It cannot actuate the aircraft, approve an intervention or declare an outcome. The application turns the chosen id back into its own proposal. The harness then revalidates that proposal, and the commander must individually approve every glass-breaking, spraying or payload-release action. Local reflexes handle motion.

Sent, per request

  • The run id and the evidence revision.
  • A bounded, truth-free evidence summary built from the command belief: up to four reports in the reporter's own words (sanitised and truncated, sent as data and never as instructions); the position estimate's support, uncertainty and room; room observation coverage; possible-occupant tracks with confidence and uncertainty; observed hazards, openings and route assessments with their ages; and remaining endurance, water and ambient temperature.
  • The harness-built candidate ids, each with a short application-written description. For Gemini, a response schema also limits the answer to those ids.
  • Fixed instructions that never include caller or candidate text.

Both models receive the same summary and candidates. OpenAI Decisions requests go to api.openai.com and Gemini requests to generativelanguage.googleapis.com; consensus sends one to each.

Never sent

  • Simulator truth, true positions or evaluator outcomes. None of these exist in the summary's source.
  • Camera or thermal images, audio and FlyVis activity.
  • The API keys. OPENAI_API_KEY and GEMINI_API_KEY are read only on the server by /api/decisions. Each goes only to its own provider, in that provider's auth header, and neither is sent to the browser or logged.

Fallback and labels. Without a key, or on refusal, an invalid choice, a 2-second timeout or an error, the deterministic local planner decides, and command shows “Local planner” with the reason. In consensus mode a disagreement, or either model failing, also leaves the choice to the local planner; one model's lone choice is never used. “OpenAI Decisions”, “Gemini” or “Consensus: OpenAI Decisions + Gemini” appears only when that choice was actually used. No model-written text is kept or shown: Gemini's one-sentence rationale is discarded. Authority and harness checks are identical in every mode, and the flight loop never waits for a cloud model.

Voice. Report intake is typed only in this build: no microphone is used and no audio leaves the machine. Any future voice intake will name its cloud providers before the microphone is used.

What is saved to MongoDB Atlas

Persistence is optional and off unless MONGODB_URI is set on the server. When it is, the workspace saves each finished simulation run once, automatically, after the simulation evaluator has posted the run's outcome, and a status line in the workspace says whether it was saved and, if not, why. UI-fixture runs are never saved: they are not simulation runs. The server stores only bundles labelled as simulation runs whose files match their recorded SHA-256 hashes, recomputes the outcome from the evaluator result rather than trusting the label sent, and never overwrites a stored run. The batch runner can upload its bundles the same way.

Stored, per simulation run

  • The run record: configuration and seed, the evaluator outcome, violations, timing and stage times, and the git commit.
  • The mission event log and the planner decision log (decider, model when recorded, latency and consensus agreement), one document per entry.
  • The recorded replay of the simulated world, gzip-compressed in GridFS.
  • Report text verbatim, inside the event log, and the commander id. Do not type real names, addresses or other personal details into reports.

Never stored

  • UI-fixture runs.
  • Camera frames, audio or browser data.
  • The connection string. MONGODB_URI is read only on the server, by the /api/runs routes and the scripts; it is never sent to the browser, returned or logged, and driver errors leave the server only as their class name.

Using saved runs. /results lists saved runs with aggregates computed in Atlas (completion, violations and median stage times by condition, controller, planner or scenario), and /replay?atlas=<runId> replays one. Search looks for words in event reasons and planner rationales across every saved run, using Atlas Search (fuzzy full text, ranked, with highlights). While the Search indexes are missing or still building it falls back to a plain text match and says so.

Access. The /api/runs routes admit only local callers, with rate limits and size caps. That is not authentication: a process on this Mac can read and add runs through them, and anyone holding the database user's credentials can read the stored runs. Runs are stored in the Atlas cluster that the connection string names, in the region chosen for it.

Simulation and limitations

  • Everything happens in a digital twin. Flight, fire, sensors, interventions and evacuation are simulated. Accelerated playback is simulation time, not real-world response time.
  • A detection is not an evacuation. “Simulated evacuation completed” appears only when the independent evaluator verifies that the simulated occupant reached the exterior assembly point within budget with no scored violation. Every other outcome reads “Incomplete — human assistance needed”. A safe abort is a safety outcome, not a rescue.
  • No automatic all-clear. One evacuation never clears a room or the house; unobserved rooms stay unknown.
  • The commander approves each intervention. Glass-breaking, spraying and payload release each need an individual approval bound to an exact proposal, revalidated against current evidence before and during execution. Abort cannot undo completed physical effects.
  • Simplified physics. The fire, smoke, ventilation and suppression models are documented simplifications, not validated fire dynamics. The thermal view is a display of simulated temperatures, not a radiometric sensor.
  • One house. Results come from a single simulated house and its seeds. They do not establish performance in unseen homes or real burning buildings.
  • Fictional aircraft. Software cannot confer heat tolerance, payload capacity or flight performance an aircraft lacks; hardware adapters are future work.
  • Motivation is not evidence. A student's account of a Troy fire motivates the work. It is not evidence that this drone would have changed that outcome.
